Renderer 规格

定义 direct 与 rendered 的分发、renderer 接口、Markdown、结构化数据和 PDF 渲染策略。

1. 责任边界

renderers-spec.html 定义 renderer 的接口、行为和失败模式。哪些扩展名进入 rendered 由 config-spec.html 维护。

2. direct 与 rendered

类型服务端职责浏览器体验
direct安全校验后返回原文件和正确 media type。浏览器直接展示或播放。
rendered读取源文件，生成安全 HTML 阅读页。用户看到项目统一样式的预览页面。

3. Renderer 接口

class Renderer(Protocol):
    name: str
    def can_render(path: Path, config: AppConfig) -> bool: ...
    def render(path: Path, request_path: str) -> HTMLResponse: ...

实现可不照搬该接口，但应保持“按配置选择 renderer、返回统一 HTML 页面、失败可回退”的设计。

4. Markdown Renderer

  • 读取文本时限制最大文件大小；默认限制见 config-spec.html。
  • 服务端渲染 Markdown，并对 HTML 做清洗或默认转义危险内容。
  • 代码块、表格和链接应有基础样式。
  • 本地相对链接应保持可点击，并继续通过 tunnel-preview 访问。

5. Structured Data Renderer

结构化数据 renderer 负责 JSON、YAML 等配置指定的结构化文本类型。

  • 解析成功时显示格式化树或格式化文本视图。
  • 解析失败时回退到带行号的安全文本视图。
  • 必须做 HTML 转义。
  • 必须限制最大文件大小，避免超大文件卡住页面；默认限制见 config-spec.html。
  • YAML 预览应尽量保留文本阅读体验；结构化树作为增强，不要求初版完整保留注释语义。

6. PDF Renderer

初版 PDF 明确归类为 rendered，不是 direct。实现采用浏览器内嵌 PDF：服务端返回统一 HTML wrapper，在 wrapper 中通过 <iframe>、<object> 或等价方式加载安全校验后的 PDF 文件。

后续可选方案：

方案优点代价
浏览器内嵌 PDF实现最轻。不同浏览器和远程环境表现不完全一致。
PDF.js体验一致，前端可控。需要引入静态资源和前端逻辑。
服务端转图片页面展示稳定。依赖重，CPU/磁盘开销更高。

已确认 MVP 采用浏览器内嵌 PDF，暂不引入 PDF.js，也不做服务端转图片。后续如体验不足，再升级到 PDF.js。

7. 统一失败模式

  • 不因 renderer 失败暴露源文件原文给浏览器下载。
  • 可返回安全错误页，说明渲染失败原因类别。
  • 解析失败但文本可读时，允许回退为安全文本视图。
  • 超过大小限制时返回明确错误页，文案使用“文件过大，请用 SSH/编辑器查看”。
维护约定：跨文档共享的默认值只在本规格中记录，其他文档引用本规格，避免重复维护。
