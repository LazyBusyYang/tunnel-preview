tunnel-preview 测试与 GitHub Actions 门禁设计

本项目要求同时具备单元测试、集成测试和 GitHub Actions 门禁。Docker build 作为发布与手动验证能力纳入 CI 设计，但不应拖慢普通 PR 的反馈。

项目：tunnel-preview 框架：FastAPI 测试：pytest CI：GitHub Actions 文档日期：2026-06-05

1. 测试目标

测试体系需要覆盖本项目的两个核心风险：文件访问边界和远程预览可用性。所有测试都应围绕“只展示允许内容、拒绝越界和隐藏内容、可稳定打开支持类型”展开。

安全边界 root 限制、路径穿越、符号链接越界、隐藏规则命中路径、未允许后缀访问。
目录体验 目录列表过滤、排序、分页、上级目录入口、点开头目录可见性和隐藏规则覆盖。
文件预览 direct 类型静态返回，rendered 类型通过项目 renderer 输出安全可读页面。
部署门禁 lint、format、unit、integration、Docker build 和容器 smoke 分层执行。

2. 测试分层

层级 目录建议 运行频率 覆盖重点
单元测试 tests/unit/ 每次 PR / push 配置解析、路径规范化、白名单判断、隐藏规则匹配、分页计算、media type 判断。
集成测试 tests/integration/ 每次 PR / push FastAPI app + 临时目录 fixture，验证 HTTP 行为和目录页输出。
容器 smoke tests/smoke/ 或脚本 手动或发布前 Docker 镜像能启动，/healthz 正常，示例目录可预览。
本项目集成测试不需要真实外部服务。应使用 pytest 的临时目录构造 fixture 文件树，并通过 FastAPI TestClient 或 httpx ASGI client 验证服务行为。

3. 单元测试要求

单元测试应尽量不启动 HTTP 服务，聚焦纯函数和小模块行为。

  • 配置文件解析：默认配置、用户覆盖、direct/rendered/hide/page_size 合并逻辑。
  • 文件类型判断：按 config-spec.html 中的 direct / rendered 配置分组测试，不在测试文档重复维护扩展名清单。
  • 隐藏规则：按 config-spec.html 中的默认 hide patterns 和 gitignore-like 语义测试。
  • 路径安全：普通相对路径、URL 编码路径、..、重复斜杠、符号链接解析。
  • 分页：默认 page_size=100，非法 page 参数回退或返回明确错误。
  • 排序：目录优先，文件随后；同类按名称稳定排序。
  • renderer 选择：direct 文件不进入 renderer，rendered 文件进入对应 renderer。
pytest tests/unit/

4. 集成测试要求

集成测试应启动完整 FastAPI app，并围绕临时 root 目录验证 HTTP 响应。

场景 预期
访问目录 返回目录 HTML；显示子目录和支持文件；不显示不支持文件。
访问 direct 文件 返回 200 和正确 content type；HTML、图片、WebP、MP4 可被浏览器直接处理。
访问 rendered 文件 返回项目渲染页面；具体 rendered 类型由 config-spec.html 维护。
访问不支持文件 返回 404。
访问隐藏规则命中路径 目录页不显示，直接访问返回 404。
路径穿越 返回 404。
符号链接 root 内符号链接允许；越出 root 的符号链接返回 404。
分页 目录项超过配置的 page size 时分页，?page=2 返回下一页。

Renderer 测试按 renderers-spec.html 覆盖解析成功、解析失败回退、安全转义和大文件限制；隐藏规则测试按 config-spec.html 和 security-spec.html 覆盖目录隐藏和直接访问 404。

pytest tests/integration/

5. 本地测试标准

本项目建议使用 Python 3.11+ 和 uv 管理开发环境。具体版本可以在实现阶段通过 pyproject.toml 固化。

uv venv .venv --python 3.11
source .venv/bin/activate
uv pip install -e '.[dev]'
ruff check .
ruff format --check .
pytest tests/unit/ tests/integration/

若实现 Dockerfile，应补充本地容器 smoke：

docker build -t tunnel-preview:local .
docker run --rm -p 5500:5500 -v "$PWD:/workspace:ro" tunnel-preview:local \
  tunnel-preview --root /workspace --host 0.0.0.0 --port 5500

6. GitHub Actions 门禁

GitHub Actions 需要拆分为快速必跑门禁和较重的镜像构建门禁。普通 PR 应快速反馈；发布镜像构建只在明确版本动作发生时运行。

Workflow 触发 是否必需 职责
ci.yml pull_request、push 到任意分支 是 ruff、format check、unit tests、integration tests。
docker.yml tag；main/release 分支上 VERSION 变化；手动 dispatch 发布前必需 Docker build，必要时 push 镜像。
container-smoke.yml workflow_dispatch；可选在 docker build 后调用 建议 启动镜像并验证 /healthz、目录页和典型文件访问。

7. Docker build 触发逻辑

Docker build 不建议在每个 PR 默认执行，以免拉长普通开发反馈。建议采用以下触发策略：

  • 任何语义化版本 tag 触发镜像构建，例如 v1.0.0 或 1.0.0。
  • 特殊 tag dev 不触发版本镜像构建，避免覆盖或混淆正式版本。
  • main 分支仅在 VERSION 文件发生变化时触发版本镜像构建。
  • release/** 分支仅在 VERSION 文件发生变化时触发版本镜像构建。
  • 手动 workflow_dispatch 可用于发布前验证，不应依赖普通 PR 自动执行。
Docker workflow 默认只 build、不 push。若后续需要发布到镜像仓库，应新增显式登录、权限和 tag 策略，不在普通 PR 中使用生产凭据。

8. 容器 smoke 验证

容器 smoke 只验证镜像能启动并完成最小预览链路，不替代单元测试和集成测试。

docker build -t tunnel-preview:local .
docker run -d --name tunnel-preview-smoke -p 5500:5500 \
  -v "$PWD:/workspace:ro" tunnel-preview:local \
  --host 0.0.0.0 --port 5500
curl -fsS http://127.0.0.1:5500/healthz
curl -fsS http://127.0.0.1:5500/
docker rm -f tunnel-preview-smoke

smoke 至少应覆盖 /healthz 和目录页。更完整的典型文件访问仍由集成测试保障。

9. 通过标准

  • ruff check . 通过。
  • ruff format --check . 通过。
  • pytest tests/unit/ tests/integration/ 通过。
  • Dockerfile 存在且可用于本地 smoke。
  • GitHub Actions 至少包含快速 CI、Docker build 和手动容器 smoke 三类 workflow。
维护约定：测试和门禁设计必须随实现同步更新；当文档与代码冲突时，以本文档和相关规格文档作为修复代码的依据。
